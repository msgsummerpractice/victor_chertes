== Exercise 8: Build Arguments (ARG) vs. Runtime Environment Variables (ENV)

In this exercise, you will learn the difference between `ARG` (available only during the build process) and `ENV` (available during build and runtime).

=== Objectives

* Use `ARG` to pass information at build time.
* Use `ENV` to set default environment variables and override them at runtime.
* Understand that `ARG` values are not persisted in the final image as environment variables.

=== Prerequisites

* Completion of Exercise 3.

=== Task

1. Modify the `Dockerfile` to include an `ARG` for the application version and an `ENV` for the greeting message:
+
[source,dockerfile]
----
FROM node:lts-alpine3.23
WORKDIR /usr/src/app
ARG APP_VERSION=1.0.0
ENV GREETING="Hello from Docker!"

COPY sources/package.json ./
RUN npm install
COPY sources/ .

# We can use ARG during the build, e.g., to create a version file
RUN echo "Version: $APP_VERSION" > version.txt

CMD ["npm", "start"]
----
2. Build the image without passing any arguments:
   `docker build -t arg-env-app .`
3. Run the container and check the greeting:
   `docker run --rm arg-env-app`
   (The app should show "Hello from Docker!").
4. Build the image again, but this time pass a custom version using `--build-arg`:
   `docker build --build-arg APP_VERSION=2.0.0 -t arg-env-app:v2 .`
5. Verify the version inside the container:
   `docker run --rm arg-env-app:v2 cat version.txt`
   It should show `Version: 2.0.0`.
6. Try to find the `APP_VERSION` environment variable inside the container:
   `docker run --rm arg-env-app:v2 env | grep APP_VERSION`
   It should return nothing, because `ARG` is not an environment variable!
7. Override the `GREETING` at runtime:
   `docker run --rm -e GREETING="Custom Greeting" arg-env-app:v2`

== Learning Outcome

* Understand that `ARG` is for build-time configuration (like versions, credentials for fetching dependencies, etc.).
* Understand that `ENV` is for runtime configuration.
* Learn how to pass build arguments using `--build-arg`.
